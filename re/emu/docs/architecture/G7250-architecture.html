Xiegu G7250 — Architecture of the Emulation & Test Solution

for a perfectly-tested, working alternative firmware platform (native OpenHPSDR P1 + TCI)

Reverse-engineering side · owner ON8ST · repo g7250-emu · companion to emulator/test study v0.5 · 2026-11-18

Clean-room, RE side. This document describes hardware facts (from the RE docs) and the design of our own emulation and test tooling. It contains no stock firmware code and no image bytes. The emulator performs no decryption: decrypted application images are user-supplied in a local image-map outside any repository and are checked only by hash. Confidence tags (VERIFIED HIGH HYPOTHESIS) are carried over from the RE docs.

The goal is an alternative firmware for the G7250 — a native OpenHPSDR Protocol-1 interface (own board id, ATU, antenna ports, 100 W PA, telemetry), plus TCI and CI-V — developed with so little risk to a real radio that it can reach release with confidence. The means to that end is a two-layer solution: an emulator that runs the unmodified factory firmware perfectly as a versioned reference baseline, and an automated test architecture on top that scores every new clean-room build and gates it toward release. Part 1 gives the hardware context; Part 2 is the heart — the full component map of the emulation and test solution; Part 3 shows how those components form a pipeline from reverse-engineering data to a tested, working platform with minimal brick risk.

Part 1 — G7250 hardware architecture (context)

The G7250 is two physically separate boxes joined by a dedicated CTRL cable: a Controller unit (touchscreen head) and a Main unit (RF, PA, baseband). Both run an STM32H7 Cortex-M7 (VERIFIED via the decompiled SystemInit routines). DC enters at the Main unit and feeds the head over the CTRL cable, never the reverse.

RF signal chain and the inter-unit cable

The receiver is a direct-sampling SDR: antenna → band-pass filter → RF ADC → FPGA → MCU DSP → CH394 → LAN. The transmitter runs the reverse through the TX DAC, the 100 W push-pull PA, the switched low-pass bank and the ATU. The MCU steers the analog path over SPI1 shift-register latches and SPI2 bias DAC, and reads forward/reflected power, PA current and temperature over ADC1.

Part 2 — Emulation & test solution architecture (the heart)

This is the full set of components that, working together, deliver a perfectly-tested alternative firmware platform. Figure 4 is the master component map; the sections below describe each layer and how control and data flow between them.

Foundation — Renode core and shared virtual time

The emulator is built on Renode (pinned version, MIT-licensed). A single shared virtual-time clock drives both machines with deterministic, serialised interleaving, so a run is reproducible to the instruction. The core also provides GDB, snapshots (a "booted" snapshot per vendor release from which test cases fork), and execution tracing with an access heatmap — the machinery that turns "does it boot" into measurable coverage. (spec §2.4)

Image source — local, no decryption

Nothing is decrypted anywhere in this tooling. The user keeps decrypted application images in an image-map directory outside any git work tree; verify.py hashes them against images/manifest.yaml (hashes and vendor-package provenance only) and refuses to run on a mismatch or if the image-map resolves inside a repository. The emulator boots the application image directly; the bootloader/flash path belongs to the firmware project. (spec §4; SECURITY.md)

Platform — two coupled machines, headless-Main primary

Two machine definitions, g7250_main.repl (H725-derived) and g7250_control.repl (H743), are wired in a .resc scene and joined by two system models: the LinkCable (the USART2 SLIP link, with byte timing and a decoder tap) and the CtrlCable (PTT, CW, power-key and audio lines plus the power domain). The primary target is headless Main (EH) — the Main machine alone, no head attached — because the alternative firmware is developed against SDR software over the network. (spec §3)

Models — the fidelity layer

Three families of models, each at the fidelity its role needs (stub / register / behaviour, spec §3.2):

  • stm32h7 blocks — RCC, PWR, FLASH, SYSCFG/EXTI, GPIO, the DMA family, USART, I2C, SPI/I²S, ADC, DAC, TIM, RTC, IWDG, CRC, and (Control) LTDC, DMA2D, FMC, SDMMC, plus a DBGMCU and an OTG stub.
  • device models — CH394 (SPI6, UDP sockets, Wake-on-LAN), the FPGA fused with GPIOE, AIC3204 codec, EEPROM, AXP223 PMIC, VersaClock 6, GT911 touch, W25Q flash, SD card, BT401, key matrix, quadrature encoders, H-22 mic.
  • system models — LinkCable, CtrlCable, the PowerModel (the H1/H2 power hypotheses, always-on, sleep/wake), the Plant (PA, detectors, NTC, relays, antenna/load so metering and TX behave), and the safety oracles that fire as hard faults.

Harness — how the suites drive and watch the emulator

A Python package g7250emu in seven layers: core (run, virtual-time clock, manifest, snapshots, record/replay), io (UART demux, the in-emulation VLAN, UDP offload, TAP/pcapng), inject (keys, encoders, touch, H-22, plant, power, fault injection), observe (traces, screenshots, audio, oracles, hang detector), protocols (P1 host, TCI client, CI-V, Icom-LAN, HDSDR, the NF-link and wake), targets (emu and the HIL adapter), and report (score, traceability). Stimuli flow from inject into the platform; observe reads traces and oracle results back; protocols exchange P1/TCI/CI-V traffic with the CH394 over the VLAN. (spec §8, §13)

Test suites — tiers, baseline scenarios and conformance

Seven tiers run from cheap to expensive: L0 static/clean-room scan, L1 model unit tests, L2 emulator integration (small clean-room test firmwares), L3 baseline regression (the A1–A12 scenarios on stock, every release in the matrix), L4 conformance of the alternative firmware (P1, TCI, optional CI-V-over-LAN, headless operation, power modes), L5 property/fuzz/fault, L6 performance and timing budgets, L7 HIL. The A1–A12 scenarios define what "runs perfectly" means for stock, captured as golden traces with a three-run determinism check.

Quality score, brick gates and targets

Every build produces one report and a verdict on a ladder: ROOD (a hard gate failed) → ORANJE (hard gates green, keep developing) → GROEN-EMU (score ≥ 75, conformance thresholds met, roll-back compatible → hand-off, gate E4) → GROEN-HIL (+ twin-validation and firmware-project gates F0–F2 → first RX-only flash) → RELEASE (+ the HIL TX steps, soak and review). Brick risk is contained by gate families E0–E4 (emulator — e.g. E0 blocks stray writes to the flash control/option registers; roll-back and power-loss tests E-B1…E-B8), F0–F3 (firmware project), and H-G1…H-G5 (HIL). The report is the only channel from the RE side to the firmware team. (spec §9, §10, §11)

Part 3 — Pipeline to a tested, working alternative platform

The four repositories form a one-way pipeline with a strict clean-room boundary. g7250-base supplies reverse-engineering knowledge as data (pinned commit). g7250-emu — this tooling — turns that into a versioned emulator plus test suites and quality reports. g7250-his is the reviewed hardware-interface spec and is the only channel by which hardware facts reach the clean-room side. g7250-fw is the clean-room firmware (NF-Main first, headless; NF-Control optional later), which reads only the HIS, public specs and the emulator's quality reports — never the images, traces or models.

Each clean-room firmware build is tested in g7250-emu in the EH configuration before anything touches hardware: it must clear the hard gates, reach GROEN-EMU, pass twin-validation against the stock baseline, and satisfy the roll-back and power-loss brick tests. Only then does it move to the HIL bench — RX-only first, then capped low-power TX into a dummy load — and only a build that survives the full HIL suite plus a soak and review is released. The emulator never removes brick risk, but by catching persistence, power and safety faults in deterministic virtual time it makes the first flash onto a real radio a last confirmation rather than a leap.
